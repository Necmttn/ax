**Goal:** Build the DuckDB-backed shared helpers the other four wave-2 chunks sit on - the typed
read helpers, the filter-clause primitive, the writer-side value contract, the file watermark, and

`layers.ts`, `testing/surreal.ts`, `shared/surreal.ts` and the three legacy read/write helper
modules. They stay until their callers - 220 files across the other four chunks - have ported.
That deletion is wave 3's `c-surreal-delete`, exactly as the backlog says.

**Spec:** `BRIEF.md` + `docs/superpowers/plans/2026-08-14-v2-duckdb-backlog.md` (chunk
**w2-lib-core**, 28 files). Template: the w1 `ax recall` vertical.

## Findings this chunk surfaces (details in REPORT.md)

1. **`ingest_file_state`'s unique index contradicts its key** - latent, not live.
   The DDL carries `UNIQUE (path)` while every writer keys rows by `(source_kind, path)`, so the
   pair is not in fact free: two source kinds watermarking ONE path is a constraint violation, not
   two rows. Pinned by a real-DuckDB test in Task 4; NOT fixed. See the retraction below.

   > **Retracted (2026-08-15), before writing the fix.** The first version of this finding claimed
   > `claude_transcript` and `claude_subagent` already watermark the SAME transcript files, making
   > this a live bug that would break w2-ingest-writers, and proposed widening the DDL index. That
   > was inferred from the two stages both watermarking "claude transcripts", and it is WRONG:
   > `transcripts.ts` walks `<project>/*.jsonl` one level deep, while `derive-claude-subagents.ts`
   > walks `<project>/<sessionId>/subagents/agent-*.jsonl` - disjoint file sets. Every non-file
   > kind uses its own sentinel path (`__pricing__`, `__closure__`, `__commit_reverted__`,
   > `__fragility_cascade__`, `pr:<key>`), and those are all distinct too. So no collision exists
   > today, the failure would be a loud constraint violation rather than corruption, and editing a
   > merged w0 DDL file for a hypothetical is the widening this chunk was told not to do. The
   > invariant is pinned by a test and documented where a writer will meet it instead. The
   > inference failed because "both stages read claude transcripts" is a statement about SUBJECT,
   > not about the file sets they enumerate - which is what the constraint is actually over.
2. **Hook-time telemetry writes cannot exist in v2.** `writeTelemetryRow` is called from
   `hooks/telemetry.ts`, which fires OUTSIDE ingest and therefore cannot hold the ingest lock -
   and the lock IS the write capability. This needs the spool treatment `w0-otlp-spool` gave OTLP,
   not a port. Raised, not fixed here.

### Task 2: the typed read helpers over `CacheRead`

**Files:** create `packages/lib/src/duckdb/query.ts` + `query.test.ts`.

Replaces BOTH legacy modules: `shared/query.ts` (structure) and `shared/graph-query.ts`
(execution). They were two files because a Surreal read needed a hand-written row mapper AND a
hand-written defensive wrapper; with `Clause` + `Schema` the structural half collapses to a record
and the execution half to five functions.

`interpolateRid` does NOT come across: DuckDB row ids are plain strings, so a record id is a bound
parameter like everything else. That is the whole injection surface the port deletes.

**Interfaces - Produces:**

```ts
export interface CacheQuery<Params, S extends Schema.Top, T> {
    readonly name: string;
    readonly row: S;
    readonly clause: (params: Params) => Clause;
    readonly mapRow: (row: S["Type"], index: number) => T;
}
export const defineCacheQuery / defineCacheSingleQuery;
export const runCacheQuery: (q, params) => Effect<ReadonlyArray<T>, never, CacheRead | ...>;
export const runCacheSingleQuery: (q, params) => Effect<T | null, never, CacheRead | ...>;
export const cacheRows / cacheFirst: (schema, clause, context) => defensive [] / null;
export interface PagedResult<T> { readonly items: ReadonlyArray<T>; readonly total: number }
export const cachePaged: (...) => Effect<PagedResult<T>, CacheReadError, CacheRead | ...>;
export const CountRow: Schema.Struct<{ total: NumberFromBigIntColumn }>;
```

The ERROR POLICY is carried over unchanged, deliberately: the defensive helpers log the caller's
context and degrade to `[]` / `null` (error channel `never`), `cachePaged` propagates. Changing it
would push error handling into 95 mechanical port sites for no gain. One addition: a
`CacheUnavailableError` is logged with its own line naming `ax ingest`, because "you have not
ingested yet" is the most common cause of an empty dashboard and the seam already wrote the
sentence that fixes it.

`count(*)` returns BIGINT, so `CountRow` exists once here rather than being re-derived (wrongly, as
`Schema.Number`) in 95 places.

- [x] **Step 1:** failing tests in `query.test.ts` against a REAL published fixture
  (`publishCacheFixture` over a couple of `session` rows): `cacheRows` decodes through the schema;
  a decode failure degrades to `[]` and logs the context; `cacheFirst` returns `null` on an empty

  `runCacheQuery` binds the clause params in order and maps rows with their index;

### Task 3: the writer-side value contract

**Files:** create `packages/lib/src/duckdb/row.ts` + `row.test.ts`.

The counterpart of `shared/surreal.ts` §1: `surrealValue` existed because every writer built
statement TEXT. Writers now hand `put`/`putMany` a `Record<string, DuckDbParam>`, and the three
conversions that are easy to get wrong live here instead of in 71 files:

- an array or nested object is JSON TEXT in a VARCHAR (the FFI client cannot decode a native
  `LIST`), so it must be `JSON.stringify`d on the way in - and read back through
  `JsonArrayColumn` / `JsonObjectColumn`;
- `undefined` is not a value: a column a writer has nothing for must bind `NULL`, and `putMany`
  refuses a ragged batch, so the row builder has to produce a STABLE column set;
- a TIMESTAMP binds as a JS `Date` (the client encodes it ISO-8601); a string that is already a
  timestamp must be converted, not passed through, or the column set silently mixes types.

**Interfaces - Produces:**

```ts
export const jsonParam: (value: unknown) => string | null;          // null/undefined -> null
export const tsParam: (value: Date | string | number | null | undefined) => Date | null;
export const textParam: (value: unknown) => string | null;          // "" -> null
export const numParam: (value: unknown) => number | null;
export const boolParam: (value: unknown) => boolean | null;
export const cacheRow: (fields: Record<string, DuckDbParam | undefined>) => Record<string, DuckDbParam>;
```

`cacheRow` maps `undefined` to `null` rather than dropping the key - dropping it is what makes a
batch ragged.

- [x] **Step 1:** failing tests. Pure: `jsonParam` round-trips arrays and objects and maps
  null/undefined to null; `tsParam` accepts a Date, an ISO string, an epoch number, and rejects
  (as null) an unparseable string; `textParam` maps `""` and non-strings to null; `cacheRow`
  keeps every declared key with `undefined` normalized to `null`. REAL DuckDB: a row written with
  `tsParam` reads back through `TimestampColumn` as the SAME instant (this is the ISO-with-`Z`
  varchar->TIMESTAMP cast, which is a claim about DuckDB, not about our code); a row written with
  `jsonParam` reads back through `JsonArrayColumn`.
- [x] **Step 2:** run -> FAIL.
- [x] **Step 3:** implement.
- [x] **Step 4:** run -> PASS.
- [x] **Step 5:** commit `feat(v2): the writer-side value contract for cache rows`.

### Task 4: the file watermark over `CacheWrite`

**Files:** create `packages/lib/src/duckdb/watermark.ts` + `watermark.test.ts`; modify
`packages/lib/src/stable-id.ts`, `packages/schema/src/duckdb-recipe-coverage.test.ts`.

Seven other `ingest_file_state` writers exist beyond the three `fileWatermark` callers (git,
pricing, closure, github-pr cooldown, commit-reverted, pr-merge-dirty, fragility-cascade), each
with its own hand-rolled digest and its own SELECT/UPSERT pair. The v2 module owns the row id and
the row shape for ALL of them, so `sha` / `since_days` watermarks compose instead of being
re-derived.

The one-time id-unify clean-slate does NOT come across: the cache is born empty, so there are no
legacy rows to migrate. That is the no-backward-compatibility ruling paying for itself.

**Interfaces - Produces:**

```ts
export const WATERMARK_TABLE = "ingest_file_state";
export const watermarkRowId: (sourceKind: string, path: string) => string;   // stableId contract
export interface WatermarkFields { mtimeMs?, size?, sha?, sinceDays? }
export const watermarkRow: (sourceKind: string, path: string, fields: WatermarkFields)
    => Record<string, DuckDbParam>;
export interface FileWatermark {
    unchanged(path: string, mtimeMs: number, size: number): boolean;
    commit(path: string, mtimeMs: number, size: number): Effect<void, CacheWriteError>;
    row(path: string, mtimeMs: number, size: number): Record<string, DuckDbParam>;
}
export const fileWatermark: (write: CacheWriteService, cfg: FileWatermarkConfig)
    => Effect<FileWatermark, CacheReadError>;
```

`fileWatermark` takes the writer as an ARGUMENT rather than resolving a service, because that is
what the seam makes available: `withCacheWrite` hands a `CacheWriteService` to a body, and there is
no `CacheWrite` service tag to `yield*` on purpose (Task 6's finding is the same rule biting the
hook path).

DDL: unchanged - see the retraction under finding 1. The `UNIQUE (path)` constraint is pinned by a
test that writes two source kinds for one path and asserts the LOUD failure, so a future writer
that picks a colliding sentinel meets a named test rather than a mysterious ingest error.

`ingest_file_state` moves out of `RECIPE_TODO` with a concrete `NATURAL_KEY_RECIPES` entry, per the
w1 rule that a table whose writer a chunk wires gets a real recipe.

### Task 5: `$PWD` -> the cached repository row

**Files:** modify `apps/axctl/src/pwd.ts`, `apps/axctl/src/pwd.test.ts`.

w1 split the git half (`resolvePwdIdentity`, engine-free) from the lookup half and put the cache
lookup in `queries/repository-scope.ts`. What the five CLI callers of `resolvePwdRepository`
(`sessions`, `costs`, `dojo`, `team`, `ingest` - all w2-cli-mcp) still need is the COMPOSITION,
returning the same shape they read today minus the Surreal `RecordId`.

**Interfaces - Produces:**

```ts
export interface PwdCacheResolution extends PwdIdentity {
    /** The cache's `repository` ROW id, or null when it has never seen this repo. */
    readonly repositoryId: string | null;
}
export const resolvePwdCacheRepository: (cwd?: string)
    => Effect<PwdCacheResolution, NotAGitRepoError | ProcessError | CacheReadError,
              CacheRead | ProcessService | FileSystem.FileSystem>;
```

`repositoryId` is the ROW id, not a constructed one, and not the git-derived Surreal key - the two
are different strings and `session.repository` holds the former. `null` is not an error: a caller
scoping to "here" then honestly has zero rows, which is what `--scope=all` is for.
